# README 설계

## 목적

이 저장소가 GitHub 이슈 및 Pull Request 템플릿을 공통으로 관리하기 위한 저장소임을 설명하고, 팀원이 버그 이슈를 일관된 방식으로 등록하고 처리할 수 있도록 운영 규칙을 한곳에 정리한다.

## 대상 독자

- 이 템플릿을 사용하는 개발자와 기여자
- 새 이슈를 등록하거나 열린 이슈를 triage하는 팀원
- 다른 저장소에 템플릿을 적용하려는 관리자

## 문서 구성

README는 다음 순서로 구성한다.

1. 저장소 소개
2. 제공하는 템플릿과 현재 활성화 상태
3. 디렉터리 및 파일 구조
4. 버그 이슈 작성 규칙
5. 라벨 규칙
6. triage 및 종료 규칙
7. 다른 저장소에 적용하는 방법

## 핵심 내용

- 버그 신고에는 `버그 신고` 템플릿을 반드시 사용한다.
- 버그 제목의 `[Bug] ` 접두어를 유지한다.
- 기능 제안은 향후 필요할 때 활성화하며, 사용 시 `[Feature] ` 접두어를 유지한다.
- 초기 라벨은 버그용 `bug`, 기능 제안 및 개선 아이디어용 `enhancement`만 안내한다.
- `priority:*` 라벨은 현재 사용하지 않고 운영 상황에 따라 추후 추가한다.
- 버그 신고 시 문제 설명, 재현 절차, 예상 결과, 실제 결과, 실행 환경을 필수로 작성한다.
- 등록 전에 유사 이슈를 검색하고 계정, 비밀번호, 토큰 등의 민감정보가 없는지 확인한다.
- 스프린트 시작 전에 열린 이슈를 검토하고 개발자끼리 처리 순서를 논의한다.
- 이슈 종료 전에는 실제 수정 여부와 검증 결과를 확인하도록 안내한다.

## 표현 원칙

- 한국어로 간결하고 실행 가능한 문장을 사용한다.
- 현재 운영 중인 정책과 향후 정책을 명확히 구분한다.
- 아직 정해지지 않은 절차나 우선순위 체계를 임의로 추가하지 않는다.
- 저장소에 존재하는 실제 파일 경로를 기준으로 구조와 적용 방법을 설명한다.

## 검증 기준

- README에 위 문서 구성과 핵심 규칙이 빠짐없이 포함되어야 한다.
- Markdown 제목, 목록, 코드 블록이 올바르게 렌더링되어야 한다.
- 안내한 파일 경로가 실제 저장소 구조와 일치해야 한다.
- 기능 제안 템플릿이 현재 비활성화 예정이라는 운영 방침과 문서 내용이 모순되지 않아야 한다.
